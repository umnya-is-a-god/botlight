# Усиление защиты и надёжности (ветка `dev`)

Что изменилось относительно `main` (коммит `d15ecbf`), как это проверить на тестовом сервере, что проверить не удалось и как откатиться.

Коротко о главном:

- рабочее состояние бота лежит в `./data` (git его не трогает);
- обновление только вперёд (fast-forward), без `git reset --hard` и `git clean`;
- секреты убраны из чата и из настроек;
- конфиги применяются только после проверки самой программой, с откатом;
- веб-часть работает без root;
- бэкапы шифруются ключом, пароль на сервере не хранится.

## Установка с нуля (рекомендуется для `dev`)

```shell
wget -O- https://raw.githubusercontent.com/umnya-is-a-god/botlight/dev/scripts/init.sh | sh -s YOUR_TELEGRAM_BOT_KEY dev
```

После установки напишите боту `/start`: главным админом становится первый, кто ему написал. Восстановить настройки можно через импорт бэкапа. Старые зашифрованные бэкапы (`*.enc.json`) расшифровываются паролем, который бот спросит при импорте.

Необязательные настройки задаются в `override.env` в папке бота:

- `LE_EMAIL=you@example.com` — почта для регистрации в Let's Encrypt. Без неё certbot регистрируется без почты.
- `XRAY_VERSION=latest` — собирать самую новую версию Xray вместо закреплённой `v26.9.30`.

## Что изменилось, по пакетам

### Этап А. Данные, изоляция, обновления

**1. Рабочее состояние в `./data`.**
- Настройки, конфиги Xray/AdGuard/ocserv/nginx, ключи DNSTT, токен бота (`data/config.php`) и обложка сайта лежат в `./data`. Этот каталог в `.gitignore`.
- `scripts/migrate_data.sh` запускается при каждом `make start`. Он один раз переносит файлы из старых мест (`config/`, `app/config.php`). Перед переносом делает архив оригиналов `data/backup/pre-data-*.tar.gz` и никогда ничего не перезаписывает.
- Все записи атомарные: временный файл, `fsync`, переименование, под `flock`. Если файл не читается, бот выдаёт ошибку, а не подставляет значения по умолчанию.

**2. Изоляция контейнеров.**
- Веб-часть php работает в двух пулах php-fpm без root:
  - `www` (пользователь `botweb`) отдаёт только подписки;
  - `admin` (`botadmin`) обслуживает Mini App.
- Токена бота нет ни у одного пула. Им доступны только «витрины» без секретов (`data/web`) и ключ проверки initData (`data/secrets/web.json`).
- Код, конфиги и скрипты монтируются только на чтение. Каталоги монтируются целиком, а не отдельными файлами.
- `cap_drop: ALL` и только нужные capabilities, `no-new-privileges`, лимиты памяти и процессов.

**3. Обновления.**
- `scripts/update.sh` сначала скачивает изменения и проверяет, что обновление возможно. Только потом останавливает бота.
- Ваши локальные правки уходят в `git stash`, обновление — `git merge --ff-only`. Если ветки разошлись, обновление не ставится, и бот об этом сообщает.
- Токен передаётся curl через временный файл, а не в командной строке.
- Автообновление ставит только подписанные теги. Ключ подписи кладётся в `data/update-signing-key`, см. ниже.
- Обновления и смену ветки делает только главный админ, с подтверждением и списком изменений.

### Этап Б. Живучесть, SSL, безопасное применение конфигов

**4. Живучесть.**
- `restart: unless-stopped` у всех контейнеров.
- Процессы (бот, cron, iplimit, sshd, php-fpm) запускаются через `scripts/supervise.sh` и перезапускаются при падении или зависании (по heartbeat-файлам).
- Healthcheck'и у php, service и ng.
- Каждый шаг cron-цикла выполняется отдельно: ошибка одного шага не останавливает остальные.

**5. SSL.**
- certbot хранит данные в `data/letsencrypt`, проверка домена — через `data/acme`. Получение сертификата идёт в фоне (`php task.php cert`).
- Ежедневная проверка продлевает сертификат, когда остаётся треть срока. «renew SSL» предупреждает о лимитах Let's Encrypt.
- Свой сертификат загружается одним файлом (ключ + цепочка) и проверяется перед установкой.

**6. Применение конфигов.**
- Новый конфиг сначала проверяется самой программой:
  - `nginx -t`;
  - `xray run -test`;
  - `AdGuardHome --check-config`;
  - `ocserv -t`.
- Если программа запустилась, но сразу упала, возвращается предыдущий конфиг (`*.prev`), и админу приходит сообщение «config … rejected».
- Если контейнер недоступен, конфиг записывается без проверки, и это пишется в лог.

### Этап В. Подписки, Mini App, админы, секреты

**7. Подписки и Mini App.**
- Параметры ссылок sing-box/mihomo передаются как JSON (base64url). Старые ссылки (`base64(serialize)`) продолжают работать: читаются без классов и с ограничением глубины.
- Mini App открывается только внутри Telegram. Данные входа (initData) передаются в теле запроса, должны быть не старше часа и проверяются ключом бота.
- Mini App и панель AdGuard живут на отдельном случайном пути (`adminhash`), не на том же, что подписки.
- nginx ограничивает частоту запросов к подпискам, Mini App и DoH. Адреса из ignorelist и мост в ограничение не попадают.

**8. Стабильные кнопки.** Кнопки ссылаются на записи по стабильным id: uuid пользователя Xray, короткий хеш для списков, пользователей OC и upstream. Удаление или сдвиг записей больше не приводит к действию над чужой записью.

**9. Админы.**
- Главный админ — первый, кто написал боту.
- Опасные действия (добавить или удалить админа, обновление, импорт, отладка) доступны только ему и требуют подтверждения.
- Бот отвечает только в личных чатах.

**10. Секреты.**
- Пароли AdGuard, OpenConnect, DNSTT и ключ WARP+ хранятся в `data/secrets`. В чате они показываются маской (`••••-AB12`), целиком — в Mini App, в разделе «Секреты».
- Приватный ключ Reality, токен WARP и WARP-профиль в чат не попадают никогда.
- Пароль бэкапа не хранится. На сервере лежат только открытый ключ и соль: Argon2id → seed → X25519. Автобэкапы шифруются sealed box, при восстановлении бот спрашивает пароль.
- Старые бэкапы (AES-256-GCM) по-прежнему восстанавливаются.

### Этап Г. Сервисы

**11. Логи.** Ротация ежедневно или при размере больше 50 МБ, хранятся 7 дней (`copytruncate`, сжатие). Расписание автоочистки убрано, ручные кнопки очистки остались.

**12. AdGuard.**
- `allowed_clients` включён по умолчанию: внутренние сети, клиенты OpenConnect, включённые пользователи Xray (по ClientID).
- Панель открывается из Mini App без страницы входа. nginx проверяет cookie (новое значение каждый день) и сам логинится в AdGuard отдельным пользователем `bot`.
- «Сторонний браузер» убран.

**13. Xray.**
- Пользователи добавляются, удаляются и включаются через API Xray, без перезапуска.
- Кнопка «новая ссылка подписки» в карточке: новый uuid, а имя, статистика, шаблон и состояние вкл/выкл сохраняются.
- Предпросмотр ссылок в сообщениях с подписками выключен.

**14. WARP.**
- Перерегистрация собирает новый профиль в отдельном каталоге и подменяет рабочий, только если WireGuard с ним поднялся. Иначе возвращается прежний.
- `start_wp.sh` не падает при ошибке: повторяет регистрацию и подъём WireGuard, а socks-прокси запускает только после поднятия WARP.

**15. Расписания и лимиты.**
- Ежемесячный сброс трафика — по календарным месяцам.
- Состояние cron (время бэкапа, месяц сброса) хранится в `data/state.json`.
- Период автобэкапа не меньше часа, автоскана логов — не меньше 5 минут. Убраны блокирующие `sleep`.
- Поиск по логам и анализ IP идут в фоне. Результат поиска приходит файлом.
- Размер загружаемых файлов ограничен: список — 5 МБ, шаблон — 1 МБ, бэкап — 20 МБ.
- Импорт пустого списка не стирает текущий.
- Бэкап проверяется целиком до того, как что-либо будет изменено.

**16. OpenConnect и DNSTT.**
- `isolate-workers = true`: ставится один раз. Если выставить вручную обратно в `false`, бот это не тронет.
- DTLS (UDP 443) идёт сразу в контейнер `oc`, минуя upstream.
- Правила iptables не дублируются при перезапуске. Клиентам VPN запрещён IPv6-форвардинг.
- Новые пароли OpenConnect и DNSTT — от 12 символов. Старые продолжают работать.
- Домен DNSTT проверяется и экранируется.

**20. Трафик OpenConnect.**
- Раз в минуту бот читает открытые сессии (`occtl` и счётчики tun-интерфейсов).
- По завершении сессии ocserv вызывает `scripts/oc_disconnect.sh`, и в `data/octraffic` пишется точный итог.
- Трафик виден в меню OpenConnect и в карточке пользователя. Сброс — кнопкой, ежемесячный — тем же переключателем, что у Xray.

### Этап Д. Гигиена

**17. Сборка и конфиги.**
- В sshd убран SHA-1 `ssh-rsa`: RSA-ключи подписывают через rsa-sha2.
- Версии закреплены: AdGuard `v0.107.79`, Go `1.27.3-alpine3.24` (сборка dnstt), Xray `v26.9.30`.
- Образы помечены меткой `org.botlight.project=vpnbot`. `make start` чистит только свои старые образы, не чужие.
- На корне сайта — пустая страница-заглушка (или ваша обложка). Остальные пути отдают 404, раньше было окно пароля и 500.
- opcache и JIT выключены для CLI-процессов.
- Добавлены недостающие переводы.

**18. Качество кода.**
- `error_reporting = E_ALL`, ошибки пишутся только в лог `logs/php_error`. Предупреждения на путях меню, карточек и подписок исправлены.
- CI (`.github/workflows/checks.yml`): `php -l`, PHPStan (уровень 1, старые находки в `phpstan-baseline.neon`), shellcheck, hadolint, `docker compose config`.
- Главное меню берёт статусы сервисов из кэша cron-цикла (раз в минуту) вместо 5 SSH-запросов при каждом открытии.
- Анализ IP использует множества вместо `in_array`: на тестовом логе в 28 раз быстрее, результат тот же.
- `app/bot.php` разбит на трейты по областям (`app/bot/*.php`), методы перенесены без изменений.
- 35 одинаковых функций запроса ввода сведены к одному `prompt()`. Поведение сверено со старой версией.

## Как проверить на тестовом сервере

Ставьте на отдельный сервер или VPS по инструкции выше. Логи: `/root/vpnbot/logs/` (`php_error`, `xray_error`, `nginx_*`) и `docker compose logs <сервис>`.

**Запуск**
1. `docker compose ps`: все контейнеры `Up`, у php, service и ng — `healthy`.
2. `/start` боту: пришло меню, вы — главный админ (Настройки → админы).
3. Главное меню: статусы Vless, OpenConnect, AdGuard — 🟢, cron — 🟢 (через минуту после старта).

**Xray**
1. Добавить пользователя, открыть карточку: ссылка, QR, подписки sing-box, mihomo, Happ.
2. Подключиться клиентом (Reality, затем WebSocket и XHTTP, если используете). Проверить, что `pgrep xray` в `xr` не перезапускался после добавления пользователя (тот же PID).
3. Выключить и включить пользователя: клиент отключается и подключается. «Новая ссылка подписки»: старая ссылка больше не работает, новая работает, статистика сохранилась.
4. Лимит IP, сброс статистики, ежемесячный сброс (переключатель).
5. Старая ссылка подписки (выданная до обновления) по-прежнему открывается.

**AdGuard**
1. Меню AdGuard → панель: открывается из Telegram без окна входа. В обычном браузере по той же ссылке — перенаправление.
2. Смена пароля, upstream, «проверить DNS», сброс настроек.
3. Allowed clients: DNS работает у включённых пользователей Xray и клиентов OpenConnect.
4. В «Секретах» Mini App виден пароль AdGuard.

**OpenConnect**
1. Подключиться клиентом (AnyConnect или openconnect). В логе клиента должен подняться DTLS (UDP).
2. Трафик в меню и в карточке растёт примерно раз в минуту. После отключения появляется точный итог.
3. Смена пароля (меньше 12 символов не принимается), камуфляж, переименование и удаление пользователя.
4. `docker compose logs oc`: воркеры не падают с `isolate-workers = true`. Если падают — см. «Не проверено».

**WARP**
1. Меню WARP: статус `on`. Маршрут через WARP работает.
2. «warp+ / перерегистрация» с ключом и без. Неверный ключ: сообщение «nothing changed», WARP работает со старым профилем.
3. Перезапуск контейнера `wp` (`docker compose restart wp`): WARP поднимается сам.

**DNSTT** (`/dnstt`): домен, пароль (от 12 символов), подключение клиентом.

**Домен и SSL**
1. Установить домен: сертификат приходит сообщением после certbot. Проверить срок в меню.
2. Свой сертификат одним файлом. «renew SSL» предупреждает о лимитах.
3. Корень сайта: пустая страница (или обложка). Любой другой путь — 404.

**Бэкап**
1. Задать пароль бэкапа. «backup» присылает `*.enc.json`.
2. Импорт этого файла: бот спрашивает пароль, настройки восстанавливаются.
3. Импорт старого бэкапа (сделанного на `main`) тоже работает.
4. Автобэкап с периодом меньше часа не принимается.

**Логи и IP**: анализ IP (кнопка 🔄 обновляет), поиск по IP (приходит файлом), блокировка и игнор, «ipinfo.io» только по кнопке.

**Обновление**
1. Кнопка «update bot»: показывает список коммитов, после подтверждения обновляет. Настройки на месте.
2. Локально изменённый файл уходит в `git stash list`.
3. Автообновление включается только при наличии ключа подписи.

**Mini App**: шаблоны sing-box/mihomo (загрузка и сохранение), «Секреты», скачивание WARP-профиля.

## Что проверить не удалось

Облачная среда, в которой делались изменения, не может собрать Docker-образы (нет доступа к репозиториям Alpine) и не может запустить весь стек. Проверено:

- `php -l`, PHPStan, shellcheck, hadolint, `docker compose config`;
- отдельные части на локальных программах: nginx, Xray 26.9.30 и 26.10.21 (конфиги всех трёх транспортов, добавление и удаление пользователей через API), AdGuard v0.107.79 (`--check-config` и вход через nginx), ocserv (`-t`), php-fpm (`-t` и права пулов), logrotate;
- миграция данных, `update.sh` на локальных репозиториях, шифрование бэкапов;
- симуляция чистой установки (миграция, `prepare`, стартовые шаги, добавление пользователя): все получившиеся конфиги приняты программами.

**Не проверено:**
- **Сборка образов** (`php83-sodium`, logrotate, пользователи `botweb`/`botadmin`, метки), `golang:1.27.3-alpine3.24` для dnstt. Первая установка покажет это сразу.
- **Работа всего стека**: SSH между контейнерами с Alpine-libssh2 без SHA-1 `ssh-rsa` (проверено только на libssh2 1.11.0 в Ubuntu); хватает ли урезанных capabilities каждому сервису; healthcheck'и и перезапуски по heartbeat; лимиты памяти.
- **ocserv с `isolate-workers = true` в Alpine (musl)**. Если воркеры падают, поставьте `isolate-workers = false` в `data/ocserv/ocserv.conf` и перезапустите `oc`: бот обратно не переключит.
- **DTLS напрямую в `oc`**, точность счётчиков трафика OpenConnect по tun-интерфейсам.
- **WARP**: регистрация `wgcf` и `wg-quick` в контейнере. Kill-switch не добавлялся: если туннель WARP упадёт уже после старта, трафик через socks пойдёт напрямую.
- **certbot** с настоящим Let's Encrypt.
- **Mini App в настоящем клиенте Telegram.** Проверка initData протестирована локально.
- **Обновление с подписанным тегом** с GitHub.
- **Сбой на сервере пользователя** (обновление `dev` → `dev`: «слетели настройки, не запустился VLESS»). Точная причина неизвестна: логов не было. Найдена и исправлена одна вероятная причина: при старте, пока контейнер AdGuard ещё поднимался, бот мог откатить конфиг AdGuard на предыдущий (`fc175df`).
- Отдельные редкие пути кода могут ещё давать предупреждения PHP в `logs/php_error`: исправлены те, что нашлись на основных путях.

**Сознательно не сделано:**
- **Подсети и IP контейнеров в `.env`.** Адреса `10.10.0.x` и `10.10.1.x` записаны не только в `docker-compose.yml`, но и в рабочих конфигах в `data/` (xray.json, AdGuardHome.yaml, ocserv.conf), в php-fpm и в скриптах запуска. Смена их через `.env` потребовала бы миграции этих конфигов при каждом изменении. Без возможности проверить это на стеке риск выше пользы. Если сеть пересекается с вашей, поменяйте адреса вручную во всех перечисленных местах.
- **`read_only` для корневой ФС контейнеров** не включён: пакетам Alpine нужна запись в `/run`, `/var` и `/tmp`. Проверить это без сборки нельзя.
- **DoH через nginx не ограничен по ClientID.** Внутренняя сеть `10.10.0.0/24` (откуда nginx ходит в AdGuard) разрешена в `allowed_clients`. Защитой служит секретный путь `/dns-query<hash>`.
- **Тег `pre-hardening`** не удалось отправить на GitHub из облака (403). Поставьте его сами:
  ```shell
  git tag pre-hardening d15ecbf && git push origin pre-hardening
  ```

## Ключ подписи обновлений (для автообновления)

Автообновление ставит только теги, подписанные вашим ключом. Положите на сервер в `data/update-signing-key` один из вариантов:

- открытый GPG-ключ (armored, `-----BEGIN PGP PUBLIC KEY BLOCK-----`);
- строку SSH allowed signers: `* ssh-ed25519 AAAA...`.

Подпись тега:

```shell
git tag -s v1.2.3 -m v1.2.3     # GPG
# или для SSH:
git -c gpg.format=ssh -c user.signingkey=~/.ssh/id_ed25519.pub tag -s v1.2.3 -m v1.2.3
git push origin v1.2.3
```

Кнопка «update bot» без ключа по-прежнему обновляет до последнего коммита ветки (только fast-forward).

## Откат

### С `dev` на `main` (на сервере, который уже работает на `dev`)

1. Сохраните настройки в открытом виде. Файл содержит все ключи и пароли: храните его только у себя.
   ```shell
   cd /root/vpnbot
   docker compose exec -T php php backup.php > /root/vpnbot-backup.json
   ```
2. Остановите бота и уберите `./data` из папки. Старый `update.sh` делает `git clean -fd` и удалил бы её.
   ```shell
   make d
   mv data /root/vpnbot-data
   ```
3. Переключитесь на старую версию:
   ```shell
   git stash -u    # если есть локальные правки
   git checkout -f main    # или: git checkout -f d15ecbf (тег pre-hardening)
   ```
4. Верните токен бота и бэкап для автоимпорта:
   ```shell
   cp /root/vpnbot-data/config.php app/config.php
   cp /root/vpnbot-backup.json update/json
   ```
5. Запустите:
   ```shell
   make u
   ```
   Старая версия при старте импортирует `update/json`, если её настройки по умолчанию, и пришлёт «import settings».
6. Проверьте меню и подключения. Затем удалите `/root/vpnbot-backup.json`. Каталог `/root/vpnbot-data` оставьте до уверенности, что всё работает.

Если автоимпорт не сработал, отправьте `vpnbot-backup.json` боту через импорт в меню.

### Обратная миграция данных без бэкапа

Если `./data` есть, а бэкапа нет, рабочие файлы можно вернуть в старые места вручную (бот остановлен, `main` уже выкачан):

```shell
cp data/pac.json config/pac.json
cp data/xray/xray.json config/xray.json
cp data/adguard/AdGuardHome.yaml config/AdGuardHome.yaml
cp data/ocserv/ocserv.conf data/ocserv/ocserv.passwd config/
cp data/up/upstream.conf data/up/deny config/
cp data/config.php app/config.php
```

Секреты, перенесённые в `data/secrets/secrets.json` (пароли AdGuard, OC, DNSTT, ключ WARP+, приватный ключ Reality), в старой версии лежали в `pac.json`. Без бэкапа их придётся задать заново, а приватный ключ Reality вернуть в `pac.json` (`reality.privateKey`). Поэтому откатываться лучше через бэкап (шаг 1).

### Оригиналы до первой миграции

При первом переносе в `./data` старые файлы архивируются в `data/backup/pre-data-*.tar.gz`. Это состояние ровно на момент перехода с `main`.
